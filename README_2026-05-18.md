## New findings (44 total)

Organized by severity. Identifier prefixes: **L** = LCEL DSL, **R** = Runtime/Tools/Structured, **B** = Backends/Streaming/MCP, **X** = Cross-cutting (guardrails/tracing/memory/RAG/agentic/build/docs).

## HIGH severity (15)

### L1. `ChatModel` propagates listener errors and skips chat-level events

**Evidence:** `llm4s-dsl/src/main/scala/org/l4j/template/llm4s/dsl/ChatModel.scala:9-26`; contract at `llm4s-runtime/src/main/scala/org/l4j/template/llm4s/runtime/RuntimeListener.scala:36-39`.

The runtime invariant is *"never propagate listener errors — a buggy tracer must not break the chat loop."* The DSL's `ChatModel` `flatMap`s on `onProviderRequest` and `onProviderResponse`, so a failing listener tears the chain down. It also fires only the provider-scope events — no `onChatStarted` / `onChatCompleted` / `onChatFailed` — so anyone using `ChatModel` instead of `AiAgentRunnable` loses chat-level correlation, never sees backend failures via the listener, and the duration timer is dropped on error.

**Fix:** Wrap each listener call in `.attempt.void`; bracket the backend call with chat-scope events; route failures through `MonadThrow.handleErrorWith` with matching `onChatFailed`.

### L2. `RunContext.apply` pins `TraceContext` at construction — every run shares a trace

**Evidence:** `llm4s-dsl/.../RunContext.scala:17-30`; `TraceContext.scala:47-51` warns *"intended to be called at the start of each chat invocation, not on every event"*. Reuse pattern visible at `src/main/scala/org/l4j/template/demo/LCEL_DEMO.scala:55-60` and `GeminiFlashTraceLcelDemoMain.scala:71-87`.

The default `traceContext0: TraceContext = TraceContext.fresh()` evaluates when `RunContext` is built, then freezes into `DefaultRunContext`. Users following the demo pattern (build ctx once, call `chain.run(input, ctx)` many times) get the *same* `traceId` across unrelated chats — the exact correlation bug `TraceContext`'s docstring warns against. There is no per-run `trace.child()` either.

**Fix:** Remove the default; require callers to supply a trace per `run`, or have each top-level `run` derive a `trace.child()` from the context.

### L3. `RunValue` adds an unsafe-cast surface for zero benefit

**Evidence:** `llm4s-dsl/.../Runnable.scala:13-25, 32-33, 70-101`.

`RunValue[F, +A] { type Value <: A; def underlying: F[Value] }` is consumed exclusively via `toF`, which immediately does `Functor[F].map(_)(identity)` to recover `F[A]`. The trait + `RunValue.apply` exists only to dodge variance on the public `Runnable[-In, +Out]`, but every combinator (`andThen`, `zip`, `map`, `assign`) then calls `self.run(...)` and re-extracts `F[Out]`. The indirection adds no abstraction and requires a `Functor[F]` constraint at every `run` call site that did not previously need one.

**Fix:** Drop `RunValue`/`runValue`; make `Runnable.run` the single primitive returning `F[Out]`. The existing `[-In, +Out]` variance works because `F[Out]` only appears in return position.

### L4. Leaf builders evaluate user functions synchronously, so exceptions escape `F`

**Evidence:** `Runnable.scala:38-45` (`fromFunction`, `pure`); `Input.scala:6-14`; `PromptTemplate.scala:17-28, 40-58`; `TextOutput.scala:7-10`.

All these build `Applicative[F].pure(f(input))` — `f(input)` runs *before* `pure`, so a throwing renderer (a `PromptTemplate` doing string interpolation on a `null`, an `Input.pick` hitting a missing key) bubbles out as a raw JVM exception instead of into the `F` channel. For `IO` users this breaks referential transparency and turns a `MonadThrow.attempt` into a no-op for those branches.

**Fix:** Route user code through `MonadThrow[F].catchNonFatal(...)` or `Sync[F].delay(...)`. Tighten typeclass bounds accordingly.

### R1. Listener errors break the chat loop — violating the documented contract

**Evidence:** `RuntimeListener.scala:36-39` (contract); `AiRuntime.scala:98,102,130,134`; `ToolLoop.scala:66,70,97,104,109,114,116`; `StreamingAiRuntime.scala:44,54,59,64`.

Every listener call is sequenced directly into the for-comprehension. A buggy tracer (Natchez span backend hiccup, exporter timeout, custom callback bug) tears the whole chat down and surfaces a tracer error to the caller — the exact failure the docstring promises to prevent. There is no test asserting the contract.

**Fix:** Introduce a private `def safe(fa: F[Unit]): F[Unit] = fa.handleError(_ => ())` and use it at every listener call site across `AiRuntime`, `ToolLoop`, and `StreamingAiRuntime`. Add a regression test with a listener that throws on every callback.

### R2. `chatRequest` silently overwrites caller-supplied `request.tools` with `toolKit.schemas`

**Evidence:** `AiRuntime.scala:93` (`val initial = request.copy(tools = toolKit.schemas)`); same pattern at line 169-172 on every loop iteration.

`ChatRequest.tools` is part of the public API, but the runtime clobbers it with whatever the `ToolKit` holds (default `ToolKit.empty[F]`). A caller who attaches schemas to a `ChatRequest` and forgets to pass a matching `ToolKit` sends zero tools to the provider with no warning. `AiAgent.chat` already merges `effectiveTools.schemas` before calling `chatRequest`, so the runtime's second clobber is redundant but still authoritative.

**Fix:** Either `require(request.tools.isEmpty || request.tools.map(_.name).toSet == toolKit.names, ...)`, or merge `request.tools ++ toolKit.schemas` (deduped), or document the precedence and warn when the caller's tools are dropped.

### R3. `decodeOrRaise` raises bare `RuntimeException(String)` — regression vs CODE_REVIEW #1

**Evidence:** `llm4s-structured/.../StructuredOutputRuntime.scala:38-41` (`MonadThrow[F].raiseError(RuntimeException(error))`).

CODE_REVIEW #1 explicitly moved the runtime off `RuntimeException(String)` to `AiRuntimeError`. The structured-output path on the *exact same boundary* (assistant output → caller-visible failure) still raises a stringly-typed `RuntimeException`. Callers can't pattern-match on "structured decode failed" vs. "tool failure" — they have to grep the message.

**Fix:** Add `final case class StructuredDecodeFailed(schemaName: String, raw: String, detail: String) extends AiRuntimeError(...)` and raise that. Preserve the underlying decode message.

### B1. AHC streaming applies `requestTimeout` as a hard wall-clock cap on the entire stream

**Evidence:** `AhcOpenAiStreamingTransport.scala:91-92`; `OpenAiCompatStreamingBackend.scala:42-43`; default at `OpenAiCompatConfig.scala:37` (60s).

`setRequestTimeout(readTimeout.toMillis.toInt)` is AHC's *total* request lifetime cap. Any SSE stream running longer than 60s — typical for long tool-augmented chats — will be force-terminated mid-stream with an exception even when the model is producing tokens steadily. SSE is fundamentally a long-lived response; the request-timeout knob must be separate from streaming.

**Fix:** For SSE, `setRequestTimeout(-1)` (no total cap) and keep only `setReadTimeout` as the inter-chunk idle cap. Or add a `streamIdleTimeout` to `OpenAiCompatConfig`.

### B2. Tool-call streaming never produces a finalized `ToolCallCompleted` event

**Evidence:** `OpenAiStreamDecoder.scala:43-54, 71`; `StreamEvent.scala:16` declares `ToolCallCompleted` but it's emitted nowhere. Decoder corpus test `OpenAiStreamDecoderCorpusSpec.scala:29-45` confirms only deltas come out.

Consumers can't drive a streaming tool loop from `StreamEvent` today. OpenAI streams `id`/`name`/`arguments` across many chunks (only the first has `id`+`name`, subsequent chunks append by index). Without reassembly, downstream code reimplements indexed-merge logic outside the decoder, and `ToolCallCompleted` is dead API. `OpenAiStreamDecoder` is per-line stateless and *cannot* reassemble.

**Fix:** Add a stateful pipe `OpenAiStreamDecoder.reassembleToolCalls[F]: Pipe[F, StreamEvent, StreamEvent]` (or fold via `Ref`) that buffers `ToolCallDelta` by index/id and emits one `ToolCallCompleted` per reassembled call before `Completed`.

### B3. AHC `runCallback` blocks the Netty I/O thread on `Await.result(... Duration.Inf)`

**Evidence:** `AhcOpenAiStreamingTransport.scala:101-105` (`runCallback`), called from `onBodyPartReceived` (line 121), `onThrowable` (128), `onCompleted` (148).

Every AHC callback dispatches an `F[Unit]` to a `Dispatcher` and then **blocks** the Netty event-loop thread on `Await.result(future, Duration.Inf)`. Two consequences: (a) AHC's IO threads (small default pool) get pinned for the duration of every dispatched effect — under concurrency the HTTP client starves; (b) if the `Dispatcher` is being released (Resource shutdown race), `unsafeToFuture` may throw or never complete and `Duration.Inf` deadlocks the Netty thread permanently.

**Fix:** Use `dispatcher.unsafeRunAndForget(effect)` (fire-and-forget) for `queue.offer`/`outcome.complete`/listener calls — they don't logically need to block. If you must wait, use a bounded `Await` and surface a typed timeout error.

### B4. AHC streaming uses an unbounded `Queue` — no back-pressure on the SSE pipeline

**Evidence:** `AhcOpenAiStreamingTransport.scala:58` (`Queue.unbounded`), enqueued from `onBodyPartReceived` at line 121.

A slow downstream consumer (UI subscriber, a tool that stalls mid-stream) lets body bytes accumulate in memory forever. The unbounded queue also defeats AHC's `AsyncHandler.State.ABORT`/`setEnabled(false)` mechanism — there is no way to backpressure the producer through TCP.

**Fix:** `Queue.bounded[F, Option[Array[Byte]]](capacity)` with a sensible default; when full, return `AsyncHandler.State.ABORT` (or pause via `setEnabled(false)`).

### X1. `GuardedToolKit` treats *any* `GuardrailBlockedException` as a guardrail block

**Evidence:** `llm4s-guardrails/.../GuardedToolKit.scala:28-42`.

The `recover` partial function matches `GuardrailBlockedException` regardless of origin. If the wrapped `underlying.execute` itself raises `GuardrailBlockedException` (nested guarded tool, or a tool using the same exception type), the outer layer silently converts it to an `isError = true` structured tool result instead of letting the exception propagate. Real downstream guardrail failures are hidden.

**Fix:** Capture the violation only from the guardrail check — `guardrails.checkTool(call, context).attempt.flatMap { case Left(GuardrailBlockedException(v)) => F.pure(errorResult(v)); case Left(other) => F.raiseError(other); case Right(safeCall) => underlying.execute(safeCall, context) }`.

### X2. `MemoryAwareRuntime` two-arg `apply` discards any listener

**Evidence:** `llm4s-memory/.../MemoryAwareRuntime.scala:79-90`; spec `MemoryAwareRuntimeSpec` only exercises the no-listener path.

The two `apply` overloads have nearly-identical signatures; the two-arg path silently uses `RuntimeListener.noop` even when callers later try to wire one in via other paths. There is no way to attach a listener after construction. Adopters relying on `onMemoryRead`/`onMemoryWritten` get silent event drop.

**Fix:** Collapse to one constructor with `listener: RuntimeListener[F] = RuntimeListener.noop[F]`, or expose `withListener(...)` for late binding. Add a test asserting memory events fire with the supplied listener.

### X3. `MemoryAwareRuntime.onMemoryRead` fires under a fresh, throwaway trace context

**Evidence:** `MemoryAwareRuntime.scala:45-54, 69-76`.

The pre-chat memory read mints a new `TraceContext.fresh()`, while the post-chat `onMemoryWritten` uses the runtime's trace from `chatRequestWithTrace`. The read and write halves of one memory-aware turn carry different `trace.id` values; the Natchez adapter (`NatchezRuntimeListener.scala:137-143`) then emits `ai.event=memory.read` with a `ai.trace.id` no other span references. Production OTel/Honeycomb/Jaeger views show the most useful event pair as disconnected.

**Fix:** Refactor `chatRequestWithTrace` to accept a parent trace seed, or fire `onMemoryRead` after `chatRequestWithTrace` resolves so both halves use the same id.

### X4. `MessageWindowMemory.append` is a non-atomic read-modify-write — concurrent appends lose messages

**Evidence:** `MessageWindowMemory.scala:19-20`; contrast `InMemoryChatMemory.scala:19-20` which uses `state.update` atomically.

`append` does `underlying.messages(id).flatMap(... underlying.replace(id, trim(existing ++ messages)))` — two distinct effect steps with no atomicity contract. Two concurrent agents (or parallel `chatRequest` reusing the same `memoryId`) can both read the same `existing`, then both overwrite, losing one party's messages. The trimming makes the loss invisible because the window already drops oldest. `InMemoryChatMemory` overrides `append` precisely to avoid this race; `MessageWindowMemory` re-introduces it.

**Fix:** Push the trim into `underlying`'s atomic update — add `def modify(id)(f: List => List): F[Unit]` to `ChatMemory`, or guard each `id` with a `Semaphore`. At minimum document that this is not safe for parallel agents sharing a `memoryId`.

## MEDIUM severity (18)

### L5. `StreamingChatModel` reports cancellation as a synthetic `InterruptedException`

**Evidence:** `llm4s-dsl/.../StreamingChatModel.scala:52-63`.

On `Resource.ExitCase.Canceled` the code calls `onStreamFailed(..., new InterruptedException("stream cancelled"), ...)`. Cancellation is not a failure; in tracing dashboards it becomes indistinguishable from a real interrupt. Also fabricates an exception (with stack capture cost) on every cancel.

**Fix:** Add `RuntimeListener.onStreamCancelled` (default no-op) and call it from the cancel arm. Until that lands, emit `onStreamCompleted` and document. Do not synthesize `InterruptedException`.

### L6. `|` operator hijacks a symbol users associate with alternation

**Evidence:** `Runnable.scala:59-66` defines `|`, `>>`, and `>>>` all as `andThen`; usage in `LCEL_OPERATOR_DEMO.scala:77-80` and `LCEL_DEMO.scala:87-90`. The plan (`LCEL_DRAFT_PLAN.md:86-96`) explicitly warns against this.

`|` is read as union/alternation/parallel across Scala (`Option#|`, `cats.|+|`, Akka Streams). Here it means strictly-sequential composition. Three identical symbols (`|`, `>>`, `>>>`) for the same op make the API less, not more, discoverable.

**Fix:** Remove `|`. Pick one canonical symbol — `>>>` is the cats convention and unambiguous with `>>` from `Apply`.

### L7. Listener invariant violated when a streaming consumer cancels before pulling

**Evidence:** `StreamingChatModel.scala:19-65`.

`onStreamStarted` fires inside `Stream.eval(for ... yield)`, but `onFinalizeCase` is attached only to `backend.stream(request)`. If the consumer cancels after the eval block but before the inner `flatMap` enters the stream (or the backend errors before any element), users see `onStreamStarted` without any matching completion/failure/cancel event. Tracing systems hold spans open indefinitely.

**Fix:** Attach the finalizer to the outer composed stream (`bracketCase` over the whole pipeline), or fire `onStreamStarted` *inside* a `Stream.bracketCase`/`Resource` whose release runs the matching completion event.

### L8. `StructuredParser` discards the raw payload on decode failure

**Evidence:** `StructuredParser.scala:8-12`.

When `codec.decode(raw)` returns `Left(error)`, the runnable raises `RuntimeException(error)` — losing both the raw payload and the codec identity. Debugging a model returning subtly malformed JSON has no payload to diff against.

**Fix:** Define `StructuredDecodeError(codecName: String, raw: String, message: String)` and raise that. Mirror `llm4s-structured`'s patterns.

### L9. No tests for parser failure, model failure, or streaming cancellation

**Evidence:** `ChatModelSpec.scala` (no error-path test); `StreamingRunnableSpec.scala` (only success); `RunnableSpec.scala:30-49` (only `zipPar` covers failure).

Three failure modes adopters hit on day one — parser on malformed output, backend raising, streaming cancel — are untested. Future changes to error semantics will break adopters silently.

**Fix:** Add tests for: backend `raiseError` → `chain.run.attempt` is `Left` and listener saw chat completion/failure events; `StructuredParser` on `Left(...)` raises typed error containing raw text; `StreamingChatModel` cancellation fires the cancel branch without `onStreamFailed`.

### L10. `Input.pick` advertises key-based selection but is just `map`

**Evidence:** `Input.scala:11-14`; plan example at `LCEL_DRAFT_PLAN.md:109`.

`pick[F, In, Out](label)(f: In => Out)` is identical to `fromFunction(f).named(s"input-$label")`. The `label` parameter influences only the graph node name — but the name `pick` and the plan's `Input.pick("question")` strongly imply field selection from a map/record, paired with a downstream `Assign("sources")` reading by the same key.

**Fix:** Rename to `Input.map(label)(f)`, or implement the implied semantics by writing the result into a `RunState`/scratchpad keyed by `label`.

### R4. `ToolKit` doc claims `LinkedHashMap` ordering, but uses unordered `immutable.Map`

**Evidence:** `ToolKit.scala:21-23` doc; `:43, :48, :82` use `Map.empty`/`toMap`.

`entries: Map[String, ToolEntry[F]]` is `scala.collection.immutable.Map`, which gives HashMap ordering once size > 4. The doc claim ("preserved by LinkedHashMap semantics") is false. Adopters relying on it (stable wire snapshots, providers that treat tool order as tiebreak) see flapping output once they register a fifth tool.

**Fix:** Switch to `scala.collection.immutable.SeqMap[String, ToolEntry[F]]` (insertion-order preserving). Add a regression test pinning observed order.

### R5. `ToolDefinition` argument-decode failure is invisible to the listener

**Evidence:** `ToolDefinition.scala:68-77` vs `ToolLoop.scala:96-98`.

When the model emits malformed JSON arguments, `ToolDefinition` returns `ToolResult.StructuredJson(isError=true)` *inside* the success branch. From `ToolLoop`'s view the tool succeeded — `onToolSucceeded` fires, `onToolFailed` doesn't. Metrics wired on `onToolFailed` show 0 failures even when every call drops a schema-violation error back to the model. Same blindspot for executors that deliberately return `isError = true`.

**Fix:** Inspect `result.isError` after `executor.execute` and route to `onToolFailed` with a synthetic `ToolFailed`, OR add `onToolReturnedError(call, ctx, result, durationNs)` so adopters can distinguish "thrown" from "returned-as-error".

### R6. `AiAgent.withConfig` drops the listener wired at construction

**Evidence:** `AiAgent.scala:83-84` (uses 2-arg `AiRuntime[F](backend, c)`); the listener-aware overload exists at `AiRuntime.scala:24-29`.

`AiAgent.apply(backend, tools, config, listener)` installs a listener into the underlying runtime. The first `agent.withConfig(c.copy(maxTurns = 16))` silently reverts to `RuntimeListener.noop` — re-introducing exactly the "silently duplicated/lost state" hazard CODE_REVIEW #12 set out to fix. The `withConfig` doc even claims it's "the *one* boundary where copying is correct," but it's also the boundary where observability disappears.

**Fix:** Store the listener as an `AiAgent` field and pass it to `AiRuntime[F](backend, c, listener)` in `withConfig`. Plumb the listener through every public overload.

### R7. Timing measurements captured at IO construction, not at IO execution

**Evidence:** `AiRuntime.scala:94` (`val started = MonadThrow[F].pure(System.nanoTime())`); `:131` (`providerStart = System.nanoTime()` inside for-yield); `ToolLoop.scala:94`. Contrast `StreamingAiRuntime.scala:42` which correctly uses `Sync[F].delay`.

`System.nanoTime()` is evaluated at the moment the wrapping IO *value* is constructed, not when it runs. For `val program = runtime.chatRequest(...)` built once and run later/repeatedly, the captured `startNanos` reflects construction time, so `durationNanos` includes idle wall-clock or goes wildly wrong on re-run. Streaming runtime already shows the right pattern.

**Fix:** Add a `Clock[F]` (or `Sync[F]`) constraint; capture `start` via `Clock[F].monotonic` or `Sync[F].delay(System.nanoTime())`. Same fix lets you defer the `val trace = TraceContext.fresh()` at line 92 so each *execution* gets a fresh trace.

### R8. `ToolLoop` `parTraverse` cancellation silently loses completed tool results

**Evidence:** `ToolLoop.scala:56, :72-73` (`FailFast → raiseError`).

With `unknownToolPolicy = FailFast` (default), if a model emits 3 parallel tool calls and the first one checked is unknown, `parTraverse` short-circuits and cancels the other two in flight. The assistant's `toolCalls` entries 2 and 3 produce no corresponding `tool` messages. Most providers reject the next turn ("each tool_call must have a tool response") and the surfaced error becomes confusing. Same hazard for `toolFailurePolicy = FailFast`.

**Fix:** For FailFast, `parTraverse` but `attempt` each per-call effect; preserve successful results, then raise after collecting. Add a test exercising "one unknown + two known parallel tool calls".

### B5. AHC streaming error body is unbounded and may be empty on common errors

**Evidence:** `AhcOpenAiStreamingTransport.scala:99, 123, 143`.

A malicious or misbehaving server returning a multi-GB non-2xx body will OOM the JVM. Conversely, for empty-body 401/403 from gateways, the resulting `OpenAiHttpError.Unauthorized("")` carries no actionable message.

**Fix:** Cap `errorBody` at e.g. 16 KiB; when empty include `s"<no body; status=$status>"`.

### B6. No retry / backoff for 429 and 5xx anywhere in the HTTP path

**Evidence:** `SttpOpenAiTransport.scala:67-93` (no retry); `OpenAiHttpError.scala:20, 24` defines `RateLimited` + `Server` but neither carries `Retry-After`; `HttpMcpTransport.scala:23-29`.

429s are routine on hosted providers; 5xxs are routine on local runtimes (osaurus/llama.cpp restarting). Every transient failure is a hard error and the chat/tool loop dies. No `Retry-After` surfacing for callers who would build retry policies themselves.

**Fix:** Opt-in retry policy on `OpenAiCompatConfig` keyed by status class with exponential backoff + jitter. Parse `Retry-After` into `OpenAiHttpError.RateLimited(retryAfter: Option[FiniteDuration], body: String)`.

### B7. `McpProtocol.decodeResponse` allows responses with missing `id` to slip past

**Evidence:** `McpProtocol.scala:79-84`; checked via `responseId.exists(_ != id)` in `StdioMcpTransport.scala:25-30` and `HttpMcpTransport.scala:32-37`.

`decodeResponse` returns `Option[Long]` for id. `responseId.exists(_ != id)` means **if id is absent, no error is raised**. A server (or stale/cached response) that omits `id` is accepted as the response to whatever request was in flight. Undermines the new HTTP id-validation test.

**Fix:** Change to `responseId.forall(_ == id) && responseId.isDefined`, or fail in `decodeResponse` itself (JSON-RPC 2.0 requires `id` on responses, even errors). Add regression tests for both transports.

### B8. `HttpMcpTransport` non-success HTTP responses lose status code and wrap as bare `RuntimeException`

**Evidence:** `HttpMcpTransport.scala:29` (`response.body.left.map(RuntimeException(_))`).

When an MCP HTTP server returns 401/403/5xx, sttp returns `Left(body)`; the code drops status, drops headers, re-raises generic `RuntimeException(body)`. Compare `OpenAiHttpError` for the OpenAI transport (typed hierarchy). Callers can't programmatically distinguish auth failures from server errors.

**Fix:** `McpHttpError(statusCode: Int, body: String) extends RuntimeException`; thread `response.code.code` into it.

### B9. `OpenAiStreamDecoder` is silently lossy on choices array and on parse errors

**Evidence:** `OpenAiStreamDecoder.scala:25-27` (`choices.headOption.toList.flatMap(decodeChoice)`); `:16-23` (parse errors silently swallowed with `Try.toOption.toList`).

(a) For `n>1` (multi-completion streaming) only choice 0 is decoded; everything else dropped without warning. (b) Any malformed `data:` frame is silently dropped — no listener hook, no counter. A provider whose schema drifts becomes "the stream is mysteriously empty." A debug listener would have caught the prior tool-call reassembly gap immediately.

**Fix:** Decode all choices into one event-per-choice preserving `choice.index`, or reject `n>1` up front. Add a parse-failure listener seam (extend `HttpListener` or new `StreamDecoderListener`).

### X5. CI builds `compile` only against root, then runs `all/test` — missing cross-module compile coverage

**Evidence:** `.github/workflows/ci.yml:58` (`sbt ++${{ matrix.scala }} scalafmtCheckAll compile all/test`).

`compile` without a project scope compiles only the root demo. Sub-modules get compiled implicitly by `all/test`, but format and warning state for sub-modules is never gated independently — a sub-module emitting new `-Wunused`/`-Wnonunit-statement` warnings can pass CI undetected via the `Test` source set. Also matters once `-Xfatal-warnings` lands.

**Fix:** Change to `sbt ++${{ matrix.scala }} scalafmtCheckAll all/compile all/test`.

### X6. `AgentScope` is a typed bag keyed by raw `String` — silent collisions, erased generics

**Evidence:** `AgentScope.scala:9-22`; usage at `SupervisorAgent.scala:23` (`scope.put(s"$name.plan", steps)`) and `Agent.scala:32` (`scope.put(agentName, output)`).

Two `WorkflowAgent`s with the same `agentName` silently overwrite each other. Generic erasure means `scope.get[List[Int]]("k")` and `scope.get[List[String]]("k")` both succeed on a `List[Any]`. Runtime type confusion bugs inside `SequenceWorkflow`/`ParallelWorkflow` become trivially reachable.

**Fix:** Introduce a phantom-typed key (`Key[A](name: String)`), or namespace keys by agent path (`scope.put((agentName, callId), v)`), and warn on collision.

### X7. `RetryPolicy` retries non-recoverable cancellations and has no time bound

**Evidence:** `RetryPolicy.scala:12-19`; usage at `GuardedChatBackend.scala:17`.

The recursive `loop` only checks `shouldRetry(error)`. With `RetryPolicy.retryAll`, a cooperative cancellation (surfaced as `CancellationException` outside `MonadCancel.canceled`) is retried like any other error, defeating cancellation. No backoff, no jitter, no max cumulative duration — unsuitable for any real provider retry surface.

**Fix:** (1) Carve `CancellationException`/`InterruptedException` out of `shouldRetry` by default; (2) require `Temporal[F]` and add a `delay` schedule with jitter; (3) add a `maxTotalDuration` bound.

### X8. `PgVectorEmbeddingStore.search` calls `parameters.result()` twice on the same builder

**Evidence:** `PgVectorEmbeddingStore.scala:104, 107`.

`parameters` is `List.newBuilder[String]`. Calling `result()` twice on a `ListBuffer`-backed builder works today (it returns the same `toList` because `exported` is just a flag), but the pattern is implementation-defined. A future stdlib change or alternate builder would silently double the count, corrupting `trailingIndex` and causing every search to bind the query vector to position 2 and overwrite an earlier parameter.

**Fix:** Bind once: `val params = parameters.result(); val trailingIndex = params.size + 2`. Use `params.zipWithIndex.foreach(...)`.

### X9. `WorkflowAgent.liftScoped` overwrites on the same agent name

**Evidence:** `Agent.scala:28-33`; `SupervisorAgent.scala:32-34`.

`liftScoped` writes `scope.put(agentName, output)`. Same agent running twice (loop, parallel-fan-out, supervisor with two `PlanStep("foo")`) silently overwrites. `SupervisorAgent` mitigates with `s"$name.$index.${step.agentName}"` *but also* calls `agent.run(...)` which writes to the raw `agentName` key — two stored copies plus overwrite of the first invocation. Tests at `AgenticWorkflowSpec.scala:36-39` use distinct agents and never trigger this.

**Fix:** Either (a) make `liftScoped` namespacing explicit (`s"$agentName.${UUID}"` or index from `AgentScope`), or (b) document the overwrite semantic and provide `liftAppending` that stores into a list.

### X10. Natchez adapters fire `Trace.attachError` even on retried (transient) failures

**Evidence:** `NatchezRuntimeListener.scala:120-135`, `NatchezHttpListener.scala:45-60`, `NatchezWorkflowListener.scala:29-36`.

`onToolFailed` attaches error to the current span regardless of `willRetry`. A tool that fails on attempt 1 and succeeds on attempt 2 marks the ambient chat span as errored, polluting error-rate dashboards and triggering alerts. Same for `onHttpFailure` and instrumented-agent failures wrapped in retries. `NatchezAdapterSpec.scala:69-86` only asserts attachment happens at all.

**Fix:** In `onToolFailed`, only `attachError` when `willRetry == false`; otherwise emit a `tool.failed.retrying` event without span-level error marking. Add a "retryable" signal to `HttpListener` if/when present.

## LOW severity (11)

### L11. `Runnable` collides with `java.lang.Runnable` under wildcard imports

**Evidence:** `Runnable.scala:9` defined; imported via `import org.l4j.template.llm4s.dsl.*` in all three demo files (`LCEL_DEMO.scala:10`, `LCEL_OPERATOR_DEMO.scala:10`, `GeminiFlashTraceLcelDemoMain.scala:6`).

`java.lang.*` is auto-imported. Users defining `class X extends Runnable` get the DSL trait, not the JVM type. IDE auto-imports often confuse the two; error messages with `Runnable[F, In, Out] vs Runnable` are terrible. `ChatModel` and `Input` are similarly common identifiers.

**Fix:** Rename to `AiRunnable`/`Step`/`Chain`/`Pipe`, or document qualified-import-only and use named imports in demos.

### L12. `WorkflowRunnable.apply` allocates a fresh `AgentScope` per `run` with no warning

**Evidence:** `WorkflowRunnable.scala:17-22`; behaviour pinned by `WorkflowRunnableSpec.scala:11-29` ("counter resets between runs").

Adopters wrapping a `WorkflowAgent` that accumulates across calls find that `WorkflowRunnable` silently destroys that state. The escape hatch `withScope` exists, but neither scaladoc nor demos make the difference visible.

**Fix:** Scaladoc contrast on `apply` vs `withScope`; consider renaming `apply` → `freshScope`/`ephemeral` so the boundary lives in the API name.

### R9. `InvocationContext.scala` file in `llm4s-runtime` contains `RuntimeConfig` + `ToolErrorPolicy`

**Evidence:** `llm4s-runtime/.../InvocationContext.scala:1-33`.

Post PR-14 the `InvocationContext` type was relocated to `llm4s-core`; the file kept its old name to host the back-compat alias plus *unrelated* types. Navigating by filename, scaladoc, and IDE "go to definition" all lie.

**Fix:** Rename file → `RuntimeConfig.scala`; move the alias to a tiny `package.scala`, or delete the alias and update the few `runtime.InvocationContext` import sites to point at core.

### R10. `executeAll` back-compat overloads mint fresh trace contexts, breaking correlation

**Evidence:** `ToolLoop.scala:14-30, :32-42`.

These two shims exist for callers that "don't carry a TraceContext." Internally nothing calls them — `AiRuntime.loop` always uses the 7-arg overload. Any external caller routed through one of these shims emits tool events under a brand-new root trace, severing the parent-chat correlation the PR-8b TraceContext work added. Convenience that defeats the feature.

**Fix:** Delete the back-compat overloads (pre-1.0; PR comments call out their lineage). Or have them require an explicit `TraceContext` with no default.

### B10. `StreamingAiRuntime` reports cancellation as `InterruptedException` with a string message

**Evidence:** `StreamingAiRuntime.scala:61-72`.

Same shape as L5 but in the streaming runtime layer. Cancellation reported as a fabricated `InterruptedException` is indistinguishable from real interrupts in dashboards and SLO breakdowns.

**Fix:** Add `RuntimeListener.onStreamCancelled(trace, request, n, durationNanos)` (default no-op); call from the `Canceled` arm; keep `onStreamFailed` for actual errors.

### X11. `WorkflowError`'s `cause: Throwable | Null` is awkward dead surface

**Evidence:** `WorkflowError.scala:3-4`.

`cause: Throwable | Null = null` is Scala 3 explicit-null union, passed straight to `RuntimeException(message, cause)`. Downstream code reading `error.getCause` (e.g. `NatchezRuntimeListener.scala:69, 134`) doesn't guard. `WorkflowError` is `sealed abstract` so external callers can't extend it — the `cause` parameter is dead.

**Fix:** `cause: Throwable = null` (Scala-2 style) or drop the parameter entirely (no current subtype uses it).

### X12. `config.yaml` / `AGENTS.md` / `README.md` drift from current module list; review filename casing inconsistent

**Evidence:** `AGENTS.md` (entire file, lines 1-13 — references graphify only, no module list); `README.md:73-85` (omits `llm4s-tracing-natchez` and `llm4s-dsl`); `config.yaml` (no schema); `readme_2026-05-17.md` (lowercase, violates project README casing — should be `README_2026-05-17.md`).

AGENTS.md no longer reflects the multi-module repo. README's layout block is missing two real sub-projects that exist on disk and are referenced from the build. No JSON schema for `config.yaml`: typing `response_format_mode: jason_schema` only fails at runtime.

**Fix:** Add `llm4s-tracing-natchez/` and `llm4s-dsl/` to README layout; extend AGENTS.md with current module list or link to `docs/USAGE.md`; rename `readme_2026-05-17.md` → `README_2026-05-17.md`; check in a JSON Schema for `config.yaml` and add an AppConfig parse test loading `config.yaml` from disk.

## Recommended order

This batch has more *correctness-and-observability* hazards than feature gaps. Suggested ordering:

1. **Make listener invariants real first (R1 + L1).** The contract is asserted in scaladoc but violated at every call site. A failing tracer should not be able to tear down a chat. One small helper closes both findings.
2. **MCP/concurrency correctness (B7 + X1 + X4).** Subtle data-loss/silent-acceptance bugs that won't show up until production.
3. **Streaming transport (B1 + B2 + B3 + B4).** The AHC transport is now end-to-end testable, so each fix can land with a specific regression test. Order: B1 first (it makes streams *survive*), then B3+B4 together (Netty thread blocking + backpressure are one rewrite), then B2 (`ToolCallCompleted` reassembly — unblocks a real tool-streaming surface).
4. **Tracing/timing correctness (X3 + R7 + X10 + L2).** All four collectively determine whether your traces are usable in OTel/Honeycomb dashboards. R7 (timing captured at construction) is the most likely to bite under cats-effect interpretation patterns.
5. **DSL surface hygiene (L4 + L8 + L6 + L11).** Easier to fix now than after adopters lock in. L4 (synchronous user-fn evaluation) is the highest-impact of these — IO referential transparency is part of the implicit contract.
6. **Regressions vs. CODE_REVIEW (R3 + R6 + R9).** Each is a small, localised fix that brings the "fixed" status of the prior review back into truth.
7. **Build/docs hygiene (X5 + X12).** Low effort, high leverage for future contributors.
8. **Remaining medium/low.** Pick from the list as time allows.
