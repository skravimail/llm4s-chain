## Findings

### 1. High: the default parallel guardrail path silently drops non-blocking transformations

Evidence:

- `llm4s-guardrails/src/main/scala/org/l4j/template/llm4s/guardrails/GuardrailChain.scala:28-46`
- `llm4s-guardrails/src/main/scala/org/l4j/template/llm4s/guardrails/GuardedChatBackend.scala:16-22`
- `llm4s-guardrails/src/main/scala/org/l4j/template/llm4s/guardrails/GuardedToolKit.scala:27-30`
- `llm4s-guardrails/src/test/scala/org/l4j/template/llm4s/guardrails/GuardrailsSpec.scala:103-112`

Why it matters:

- `checkInput`, `checkOutput`, and `checkTool` all return the original request/response/tool call via `.as(request)`, `.as(response)`, and `.as(call)`.
- That means any guardrail returning `GuardrailResult.Allow(modifiedValue)` has its modification discarded in the default path.
- `GuardedChatBackend` and `GuardedToolKit` both call those default methods, so transformation-style guardrails only work in the explicit sequential APIs.
- The current tests prove transformation chaining only for `checkInputSequential`, which leaves the default public path unverified.

What to improve:

- Split the API into explicit validator-only and transformer-capable paths, or
- preserve transformations in the default path and document the ordering tradeoff clearly, and
- add tests covering transformed input/output/tool calls through the default `GuardedChatBackend` and `GuardedToolKit` paths.

### 2. High: `StdioMcpTransport` is not safe under the runtime's parallel tool execution model

Evidence:

- `llm4s-mcp/src/main/scala/org/l4j/template/llm4s/mcp/StdioMcpTransport.scala:14-28`
- `llm4s-runtime/src/main/scala/org/l4j/template/llm4s/runtime/ToolLoop.scala:44-84`
- `llm4s-mcp/src/main/scala/org/l4j/template/llm4s/mcp/McpToolProvider.scala:16-35`

Why it matters:

- `ToolLoop.executeAll` now uses `parTraverse`, so multiple tool calls in one model turn run concurrently.
- MCP-backed tools created by `McpToolProvider` all share one `McpClient`, which in turn shares one `StdioMcpTransport`.
- `StdioMcpTransport.request` writes a line and then immediately consumes the next line from a shared `readLine`, with no mutex, dispatcher fiber, or per-id response routing.
- Two in-flight requests can steal each other's response lines; the id check only detects the mismatch after the wrong caller has already consumed the line.

What to improve:

- Serialize stdio MCP requests with a `Mutex`, or
- introduce a dedicated reader loop with pending-response promises keyed by JSON-RPC id, and
- add a concurrency test with two simultaneous MCP tool calls returning out of order.

### 3. Medium: `HttpMcpTransport` generates JSON-RPC ids but never validates the response id

Evidence:

- `llm4s-mcp/src/main/scala/org/l4j/template/llm4s/mcp/HttpMcpTransport.scala:19-31`

Why it matters:

- The transport increments `nextId` and sends the id in the request payload.
- The response path then calls `McpProtocol.decodeResult(body)`, which throws away the response id entirely.
- A buggy or misbehaving MCP server can return the wrong id and still be accepted as a successful response.
- There is currently no test coverage for `HttpMcpTransport` at all.

What to improve:

- Decode the full response and validate the id, mirroring `StdioMcpTransport`, and
- add request/response tests for success, protocol error, and id mismatch paths.

### 4. Medium: CI is miswired for this Scala 3 multi-project build

Evidence:

- `build.sbt:10`
- `build.sbt:139-155`
- `.github/workflows/ci.yml:20-23`
- `.github/workflows/ci.yml:56-69`

Why it matters:

- The build is pinned to Scala `3.3.4`, but the workflow matrix still forces `++2.13.16`.
- The repo has a dedicated aggregate project `all` specifically for `all/test`, but CI runs plain `test`.
- In practice, that means local `sbt test` only covered the root tests in this review; the full module suite required `sbt all/test`.
- Coverage is wired the same way, so the workflow's reported coverage can underrepresent the real codebase.

What to improve:

- Remove the stale Scala 2.13 matrix entry and run the repo's actual Scala 3 version, and
- switch CI test and coverage commands to `all/test` and the aggregate equivalent for coverage/reporting.

### 5. Medium: the streaming OpenAI-compatible surface is only partially implemented but documented as complete

Evidence:

- `README.md:14-15`
- `README.md:72`
- `docs/USAGE.md:64`
- `docs/USAGE.md:240-262`
- `llm4s-openai-compat/src/main/scala/org/l4j/template/llm4s/openai/OpenAiStreamingTransport.scala:6-19`
- `llm4s-openai-compat/src/main/scala/org/l4j/template/llm4s/openai/OpenAiCompatStreamingBackend.scala:10-44`
- `llm4s-streaming/src/main/scala/org/l4j/template/llm4s/streaming/StreamEvent.scala:11-17`
- `llm4s-openai-compat/src/main/scala/org/l4j/template/llm4s/openai/OpenAiStreamDecoder.scala:39-71`
- `llm4s-openai-compat/src/test/scala/org/l4j/template/llm4s/openai/OpenAiCompatStreamingBackendSpec.scala:30-56`

Why it matters:

- Production code defines the `OpenAiStreamingTransport` trait, but there is no concrete SSE/STTP transport implementation in the repo.
- The streaming backend tests use stub transports rather than a real provider-facing implementation.
- `StreamEvent` exposes `ToolCallCompleted`, but the decoder never emits it; only `ToolCallDelta` and `Completed` are produced.
- The docs currently present `llm4s-openai-compat` as an HTTP/SSE backend, which overstates what is actually shippable today.

What to improve:

- Either ship a real OpenAI-compatible SSE transport plus tool-call reassembly, or
- narrow the README/docs to describe the current state honestly as a streaming facade + decoder layer.

### 6. Medium: no-auth providers still receive an `Authorization` header

Evidence:

- `src/test/scala/org/l4j/template/demo/AppConfigSpec.scala:70-78`
- `llm4s-openai-compat/src/main/scala/org/l4j/template/llm4s/openai/OpenAiCompatBackend.scala:26-29`
- `llm4s-openai-compat/src/main/scala/org/l4j/template/llm4s/openai/OpenAiCompatStreamingBackend.scala:21-24`

Why it matters:

- The config layer explicitly models providers like Ollama as not requiring an API key and returns `""`.
- Both OpenAI-compatible backends always emit `Authorization: Bearer ${config.apiKey}`.
- For no-auth providers that becomes `Authorization: Bearer `, which some local servers ignore but stricter proxies or gateways may reject.

What to improve:

- Only emit the header when `apiKey.nonEmpty`, or
- make auth strategy explicit in `OpenAiCompatConfig` instead of encoding "no auth" as an empty string.

## Lower-priority Improvements

### 7. `LoopWorkflow` still uses direct recursion and a generic `RuntimeException`

Evidence:

- `llm4s-agentic/src/main/scala/org/l4j/template/llm4s/agentic/LoopWorkflow.scala:15-24`

Why it matters:

- `AiRuntime.loop` was already upgraded to a stack-safe `tailRecM` shape.
- `LoopWorkflow` still recurses directly inside `flatMap`, so very large iteration counts remain a potential stack-safety risk under less forgiving monads.
- It also raises a generic `RuntimeException` instead of a typed workflow error.

What to improve:

- mirror the `AiRuntime` approach with `tailRecM`, and
- introduce a typed workflow error ADT for max-iteration failures and missing-agent failures.

- `docs/USAGE.md:249`

## Recommended Order

1. Fix the guardrail API semantics before more users depend on the current default behavior.
2. Make MCP transports concurrency-safe and protocol-strict.
3. Repair CI so it exercises the real Scala version and the aggregate suite.
4. Either complete or narrow the streaming/OpenAI-compatible story.
5. Clean up docs and no-auth header behavior.
